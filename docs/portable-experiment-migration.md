# Portable experiment migration acceptance

Completion means an independently authored Workshop experiment exercises the
generic public lab path on real data, produces valid paired comparison evidence,
and replaces its legacy active path with references and tests updated. Synthetic
smoke success, copied declarations and a preparation-only PR are partial evidence.
Computation stays in native Python components, connections in the typed native
plan, execution in CampaignEngine/Controller. No dataset-specific engine or
custom driver may bypass missing contracts.

## Stage 1: local snapshot preparation

- [x] Distinct native `dataset_snapshot` artifact identity and existing typed
  preparation snapshot ports, with explicit version-2 consumption admission.
- [x] Metadata-only inspection; local native integrity/config verification;
  missing-input refusal without acquisition; public apply/resume integration.
- [x] Bounded local-fixture preparation and receipt replay without repeated work.

## Stage 2: bounded Hub acquisition foundation

- [x] Inventoried native source locks, bound output/private cache, version-3
  admission, whole-file HTTP reservations, typed Git/LFS content authentication.
- [x] Native snapshot journal, interruption/cancellation recovery and published
  artifact replay; loopback Parquet → tokenizer → pack integration.
- [x] Cumulative operational transfer/metadata/request/retry/scan/verification
  allowances and observed owned-storage stops. Unsupported hard guarantees and
  decoder options fail closed; see [the contract](preparation-recipes.md#bounded-hub-acquisition).
- [ ] Real pinned Hub delivery and decoder-resource qualification under a separate
  authorization. Loopback wiring is not TinyStories portability evidence.

## Remaining completion gates

- [ ] Portable acquisition: inventoried native source-lock references, bound
  output/cache locations, separately admitted network/download/storage budgets,
  native journal/cancellation/resume evidence. Keep retained document limits
  distinct from Hub cache traffic.
- [ ] Authenticated snapshot-backed CPU execution using the prepared identities.
- [ ] Bounded authored multi-cell Campaign connections, paired baseline/variant
  execution, declared interventions and invariants, explicit approvals and
  comparability/refusal outcomes. Completed runs alone are insufficient.
- [ ] Continuation: pinned parent generation/full-state requirements, cumulative
  budgets, scheduler/optimizer semantics and preserved parent lineage.
- [ ] Inventoried descriptive heldout suites and generation panels, retaining
  evaluation/checkpoint/prompt/decoder identities and failed/missing outcomes.
- [ ] Public final evidence collection/reporting after evaluation and panels;
  distinguish verified coverage, scientific comparability and quality claims.
- [ ] Independently authored, committed Workshop real-data proof at frozen lab,
  runtime, recipe, source, tokenizer and prepared-data pins. Retain measurements,
  paired results, evaluation/panels and replay without duplicate attempts.
- [ ] Replacement map for every legacy active sample, route, documentation link
  and test. Update references and retire replaced active material only after
  replacement proof passes; preserve historical artifacts, hashes and readers.
- [ ] Explicit disposition of hosted/GPU samples: their own qualified replacement
  or a documented distinct retained scope. CPU evidence is not accelerator proof.

The snapshot-consumption and bounded-acquisition foundations do not complete
these real-data and full-workflow gates.
Legacy paths/tests remain until their replacement is proven. A preparation recipe
revision identifies its committed inputs and admission. A later workflow recipe
revision pins the produced artifact identities. Replaying preparation must use
its original recipe revision and admission; workflow edits do not retroactively
change preparation provenance. Fresh preparation records the selected lab source
identity.

## Real-data admission

Before real acquisition/execution, record selected immutable source revision and
rights provenance, existing verified payload versus acquisition, network/cache/
storage limits, CPU runtime, all paired/continuation update budgets, pilots and
runtime probes, evaluation/panel work, monitoring and cancellation. The native
snapshot `max_work_bytes` does not cap Hub download/cache traffic. Broader hardware,
spend or additional workloads require their own authorization.
