## Preflight before full training

An initial inspect through `uv run --locked` synchronized the checkout's locked **CPU** PyTorch (`2.14.0+cpu`) over the existing vendor build. Explicit ROCm stage then rejected the unavailable backend before any study optimizer training. The user approved restoring the existing environment from `requirements/rocm-gfx1100.txt`; `uv pip install --python .venv/bin/python -r requirements/rocm-gfx1100.txt` restored `2.13.0+rocm10.0.0` (HIP 7.15.26333). The later attempt to reuse the incomplete CPU-era `staging/seed42/` correctly rejected its unfinished stage manifest. Its partial diagnostic evidence is preserved; the valid ROCm stage used a new `staging/seed42-rocm/` output. Every subsequent accelerator command uses `uv run --locked --no-sync`, with actual PyTorch device checks; no automatic host/vendor inference or CPU fallback.

Live `sparselab inspect` found the frozen dense candidate at **50,274,752 total, trainable, and active parameters/token** (hidden 704, layers 10, heads 8, FFN 1,168; no experts). The ~30M reference has 29,893,120 parameters (hidden 512, layers 8, heads 8, FFN 1,408). The scale and budget-extension configs have equal training, optimizer, data, tokenizer, evaluation, and runtime settings; their LR values match at all 16,384 updates. Static estimated peak was ~1.76 GB but fit was marked UNKNOWN until device verification; its unrequested recomputation/microbatch proposal was **not** applied.

The fresh five-update ROCm warmup in `sparselab-work/experiments/dense-lm-scale-v1/staging/seed42-rocm/stage.json` (SHA-256 `dcd9147cf3090ee7b94fb69945750985fb0afab47f3eaf050027a510d7e416e3`) and `pilots/warmup/report.json` (SHA-256 `cda14f6b2a02ef4287d34f52cc80cc57fec2811f335c2a093decd5498df94f56`) passed checkpoint reload and finite forward/backward. ROCm device: AMD Radeon RX 7900 XTX, 25,708,240,896 bytes VRAM, 24,276,099,072 bytes reported free at stage. Measured warmup peak **1,459,952,128 allocated / 1,530,920,960 reserved bytes**, ~6.0% total VRAM; no batch or sequence reduction. After excluding the first initialization update, four timed updates averaged **0.118966 s/update, 8,607 targets/s**. Extrapolated optimizer-only time at 16,384 updates was **1,949 s (~32.5 min)**; this short pilot did not establish stable full-run throughput or end-to-end wall. Historical 50M post-warmup 24-update pilot measured ~9,127 targets/s.

Preflight's 603,297,392-byte *per-checkpoint* estimate counted nine explicitly configured steps (~5.43 GB) but failed to include automatic checkpoints at all periodic validation steps. Future runs should budget at least ~49 GB per seed for these exact settings, plus metrics/stage output. At preflight the task filesystem had ~819 GiB and ~67 million inodes free; after seed 42, ~774 GiB remained. No unrelated data were pruned.

## Parameter, time and memory cost

Both arms are FP32 dense decoders on the same detected RX 7900 XTX and ROCm PyTorch `2.13.0+rocm10.0.0`: **29,893,120 → 50,274,752** total/trainable/active parameters per token (1.682×). The large model changed hidden 512→704, depth 8→10, FFN 1,408→1,168; eight attention heads remain. No Engram, MLA, MoE, or sparse attention is present. The scale candidate used microbatch 8 × accumulation 1, context training length 128, and the original 4,096-step cosine decay then 3e-5 floor. Full-state final checkpoints passed `sparselab checkpoint verify` at all three seeds; optimizer overflow retries were zero. Peak allocated/reserved large VRAM was **1,459,952,128 / 1,530,920,960 bytes** for each seed, versus **1,064,241,664 / 1,117,782,016 bytes** recorded at each accepted small terminal (large allocated 1.372×); device total was 25,708,240,896 bytes. These are allocator peaks, not model weight bytes or a power measurement.

## Parent-regression view and disposition

| Axis | Observation relative to the mature small same-seed 16.78M reference |
|---|---|
| LM learning | **IMPROVED on this split/three seeds:** lower loss at all 82 shared post-initial coordinates; terminal reductions 0.057709, 0.060708, 0.049622 nats/target. Initial large losses are higher; no evidence of a plateau or independent-domain gain. |
| Generation mechanics | **PRESERVED:** all exercised candidate checkpoints pass finite-weight/integrity, boundary, deterministic/repeatable cache/prefix and diagnostic checks. Mechanical validity does not validate narrative coherence. |
| Individual outputs | **MIXED:** two seed-specific small color contradictions disappear, but the seed-73 small case was already correct; boat continuity, wet-path causality and bread→cake drift persist or worsen elsewhere; no unusual brass-moon follow-through. Raw cases above and in evidence, never pooled into a quality score. |
| Runtime and memory | **MEASURED tradeoff:** +68.2% parameters, approximately +51% optimizer seconds and +37.2% peak allocated device memory; end-to-end comparisons have different segmentation/reporting overhead. |
| Promotion | **NONE:** no new accepted baseline, no architectural superiority or general useful-text claim; promoted `dense-lm-v1` stays unchanged. Token-budget extension remains a separate Finding, and [generation/degeneration](../../../docs/research/roadmap.md#dense-lm-v1-descendants) remains a separately proposed study. |

Within this bounded setup, the larger dense model consistently learns the held-out TinyStories targets at lower loss for a substantial time/memory cost; it does **not** consistently improve fixed generated stories. Independent data, longer runs, stronger human/blinded evaluation, decode controls, and a prespecified review would be necessary before stronger capacity or quality claims. Original small-parent versus extension source identity drift was recorded as best-effort, not bitwise code identity; all three new scale runs record the same source identity `fb979d47fa049275d78ddfe3c965cac8a6209384e74defdd491118e53a65f1a2` as the mature continuation runs. Clarification of the frozen preregistration wording: new configs/documentation are bound by their own hashes but do **not** themselves change the source-code identity hash, which covers `src/sparselab/`. The rejected partial seed-42 child and the failed CPU-era stage remain preserved rather than silently relabeled as accepted milestones.
