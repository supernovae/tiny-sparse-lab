The v4 project currently contains **58 unchanged v3 declarations and 65 new first-party declarations** (57 train, five validation, three test), with distinct `devmind-v4` and `devmind_v4_lm` identities. Independent import verified all **58** copy-on-write-intended v3 snapshots against their original receipts in the new lock. Reserve approximately **200 GB** for new Git caches, mutable indices/build and immutable release, leaving >200 GB headroom at preflight; stop before any low-margin launch. Source-level `max_bytes` caps for the 65 new declarations sum to **344,970,000 raw selected bytes** (**318,295,000 train**), not an expected retained-normalized count. Pinned-tree estimates for the reviewed subset sum to roughly **227 MB new train selected bytes**. Even a fully retained maximum from these selectors would put v4 developer text below the aspirational 1.0 GB target when added to v3's 510,860,750 bytes. Do not disguise this by filling with generated, vendored, generic or unrelated Go/C/Rust bulk; evaluate the actual measured shape coverage and 25–30% repetition at freeze against the expressly non-hard planning target.

## Source selection and heldouts

Target roughly 1.0–1.2 GB distinct retained developer training text by adding genuine first-party SQL, JavaScript/TypeScript, shell, config/IaC, build, schema, operator/runbook and real diagnostic/example material. This is a planning target, not a legal, scientific or quality gate. Prefer coherent authored sources with explanations, tests and real deployment/config examples; disallow bundled dependencies, generated schema or lockfile bulk, credentials, private fixtures and generic web/academic/math/Wikipedia expansion. Preserve existing first-party code and tests rather than relabeling them. Keep OMP tools/process/debugger/session documentation a small specialization.

Preserve whole-source heldout semantics for the preexisting PostgreSQL, SQLite, Git and Prometheus projects. Their official repositories are *not* independent train sources simply because a different path/revision is selected. Use independent eligible projects for new train-side SQL, shell and observability material; do not admit training duplicates of heldout families. New whole-source validation/test families should cover SQL, JS/TS, shell, config/IaC, build, operator and schema/API reasoning. Describe any sparse heldout shape explicitly rather than inferring isolation from an exact-hash screen. Exact normalized content and canonical-origin conflicts remove train copies; validation–test conflicts fail.

Apply the existing `allowed_unless_explicitly_prohibited` private-training source policy, inspecting governing terms, rights and file-level exceptions. Preserve attribution, notices and raw source bytes; metadata/reconstruction-only release does not publish source text. Copyleft is not a private-training veto. Model-weight licensing remains separate. Research rights issues when a candidate arises, but do not make an unsupported blanket licensing attestation or include unknown/restricted/private material.

## Measurement and decision

Stream frozen release documents to measure per-source selected versus retained bytes, developer/nondeveloper train and heldout counts, source-path language and engineering shapes, including missing categories as zero. Developer exposure for `p` of 20/25/30/35/40 percent is descriptive byte-proxy developer passes `p × nondeveloper_bytes / ((1−p) × developer_bytes)` relative to one nondeveloper pass. It is neither tokenizer token count nor a training mixture. Report exact/raw/canonical duplicate groups and a bounded lexical near-screen across train and independent heldouts. The near-screen must report both original-text similarity and independently proposed candidate similarity after *diagnostic-only* removal of recognized leading repeated license/copyright headers; never modify original source/normalized release text or erase attribution. Both modes have sampling/prefix/LSH limits, and content-bearing high-similarity candidates need review.

Use bounded-memory existing acquisition, build, dedup and frozen-release verification. Record selected-source counts and rights exclusions, progress phase timing, observed peak RSS, disk bytes/inodes and release identity. Do not launch if workspace lacks a conservative margin for additional Git caches, snapshots, mutable build and immutable release. Freeze only after LM train lineage includes every retained new train document and excludes all new heldout IDs. Prior successful v3 operation occupied 94 GB with 449 GB free on the same filesystem; recheck at launch. Preserve all negative and interrupted attempts.

The decision defaults to **`READY_FOR_TOKENIZER`** after closing the documented v3 shape gaps and obtaining meaningful independent heldouts; use `EXPAND_MORE` only for a concrete major missing domain or integrity defect that would materially undermine DevMind. The lab will learn more from an actual future tokenizer/model test than unbounded collection. A candidate release is not a claim of useful model behavior, legal weight publication or hardware fit.

## Decision: READY_FOR_TOKENIZER

The remaining real gaps are **volume and measurement**, not an absent developer domain: shell (~5.3 MB), stand-alone IaC (~0.82 MB), operator/runbooks (~7.4 MB), authored examples (~1.9 MB) and build (~3.1 MB) are still much smaller than implementation/tests, and the 1.0–1.2 GB planning target was missed. However, unlike v3, v4 now contains genuine standalone and test-harness SQL, JavaScript and much more TypeScript, shell, configuration/build/operations/schema/errors/examples; independent whole-source heldouts cover each family. The byte-proxy 25–30% passes are **1.48–1.90** over 735 MB rather than demanding an artificial 1 GB. No current *major missing domain or integrity defect* warrants an unbounded next corpus pass. **READY_FOR_TOKENIZER** is a corpus-source decision only: tokenizer fit, comparative downstream quality, model-weight rights, hardware fit and any training recipe remain separate unperformed decisions.
