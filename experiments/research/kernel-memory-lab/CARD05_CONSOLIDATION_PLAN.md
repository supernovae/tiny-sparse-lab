## Incremental implementation and validation slices

1. **Safety/readiness correctness:** extend the native monitor and baseline binding, adopt the repaired live-tree sampler and owned subreaper behavior, and test every fail-closed path. Pair this with a non-promoting readiness check that distinguishes complete execution, complete scores, threshold failure and missing evidence. Existing monitor/card05 scripts remain the control until replacement parity passes.
2. **One attempt contract:** add the content-bound optional reference and zero-update mode to existing plan/approval/ledger paths. Check cumulative updates and actual targets across all phases, plus generation limits and the single deadline. Ensure every wrapper phase sees one contract and one baseline; reject changed code/config/source identities before spawn.
3. **Panel controls and score binding:** add the two optional decoder fields and two-panel cached/uncached workflow, then bind reviewed score imports to the verified evaluation index without turning panel text into a numeric gate. Preserve the frozen 200-item suite and all old panel hashes when new fields are omitted.
4. **First consumer:** author the separate base-language supply proposal only after slices 1–3 pass in a clean pushed checkout. Use the new native contract/monitor/panel on that one approved experiment; compare their receipts with the existing Card 05 wrapper behavior, stop on any mismatch, and keep C05-N1/X1 as historical controls. Instruction, evidence-reader and agentic stages follow separate reviews and budgets.

### Test lanes and main-integration checklist

**Zero-update validation lane:** schema/identity tests, mocked GPU sensor and storage traversal, harmless subprocess trees (including detached groups, early parent exits and TERM-ignoring descendants), clock/cap/replay tests, panel parsing and mocked token trajectories, score-import completeness, `inspect`, authenticated artifact verification, Campaign `validate/status/next/explain`, and `stage --through validate` only when separately authorized. Use a positive node-ID allowlist: `tests/test_attempt_budget.py`, `tests/test_operational_monitor.py`, `tests/test_kml_card04_profile_tools.py`, and `tests/test_kml_card05_matched_diagnostic.py` are examples to review at execution time. A file name alone is not a guarantee; inspect its fixtures and subprocesses before inclusion.

**Update-bearing implementation lane:** `readiness smoke --family dense`, `stage --through smoke/warmup`, real `train`, and tests whose fixtures train, including `tests/test_generation_panel.py`, `tests/test_campaign_generation_panel.py`, `tests/test_model_readiness.py` (through `test_evaluation_suite.py`), must get their **own explicit aggregate optimizer/time allocation**. Never run broad test globs under a zero-update contract. Mocked unit tests can run earlier; a passing mock does not replace the later native runtime gate.

Before a future merge to main, require: (1) reviewed typed schemas and migration/absent-field digest compatibility; (2) targeted zero-update failure tests first, then budgeted update-bearing integration tests with persistent receipts; (3) platform-specific sensor availability and no unauthorized fallback; (4) exact ledger, selected-checkpoint, tokenizer, corpus, panel and score identities; (5) one common-root baseline, sampled peak and final byte/inode reconciliation; (6) outer deadline and zero-survivor owned shutdown on success, exception and timeout; (7) numerical/target-token and final-batch masking checks for a bounded run; (8) no automatic retry, promotion or Card 06 admission; (9) `git diff --check`, Ruff, focused and relevant broader tests, clean fixed checkout and reviewed PR; and (10) local ROCm acceptance only under a separately approved runtime envelope. The future merge itself needs its own review; this plan requests none.
