# Card 03 complete-shard rights and ingestion pilot — proposed, not approved

This proposal implements [KML-D05](DECISIONS.md#kml-d05--retain-two-common-pile-candidates-for-pilot-planning-2026-10-07) at the planning level. It supersedes the **64 MiB two-source pilot request** in [S1](results/2026-10-07-card03-specification.md), which [S2](results/2026-10-07-card03-metadata-audit.md) found infeasible. It does not change the Card 03 language/evaluation contract, admit any source row, authorize a download or grant a training budget. The goal is one rights-quarantined, deterministic sample from **one complete compressed shard of each selected Common Pile component**. PagerDuty remains the incident-response domain candidate but is outside this pilot; no Git fetch occurs.

## Proposed one-attempt limits

| Limit | Exact allocation and accounting |
| --- | --- |
| Source payload transfer | First complete copy of both files: **843,172,419 bytes**. Allow **one** retry of **one** shard only after a transport interruption; reserve the larger 480,242,750-byte Wikimedia shard as worst case. Maximum charged source payload over the entire attempt, retries and resumed invocations: **1,323,415,169 bytes**. Charge a full file's declared size before opening each transfer, even if it fails partway. No retry on SHA mismatch, malformed data, rights concern or a changed source identity. |
| Metadata transfer | At most **1,048,576 response-body bytes** for pinned tree/config/split checks. Total application-layer response-body allowance, including source payload, is **1,324,463,745 bytes**. Record this separately from physical TLS/network overhead, which is not observable precisely by the client. |
| Selection and retained text | Scan at most 4,096 JSONL records per shard; use the native revision/path/row-index hash selector with modulus 256 and remainder 0. Select at most 32 records and retain at most **33,554,432 UTF-8 bytes per component** (64 rows and 67,108,864 bytes combined). Selection failure or an oversized row stops the attempt; do not loosen these caps after seeing content. Store selected rows as **rights-quarantined**, never train/evaluation inputs. |
| Time and compute | One **2,700-second (45-minute)** wall-clock deadline from ledger creation, inclusive of metadata checks, transfer, one permitted retry, streaming scan, receipts and verification; CPU only, **zero optimizer updates, zero model target tokens, zero GPU/cloud jobs and zero spend**. No tokenizer fit, model training, Campaign apply or bulk corpus build. |
| Storage | External persistent root `/srv/sparselab/state/experiments/kernel-memory-lab/`; at most **5,368,709,120 additional bytes (5 GiB)** and **1,000 additional inodes** for the attempt, with at least **1 GiB** and 1,000 inodes free beyond the projected peak before launch. Recheck actual output and cache locations immediately before any approved run. The 2026-10-07 metadata check found about 955 GiB and 67 million inodes free on `/srv/sparselab`, not a future capacity guarantee. |

The component cards report 20.1 GB and 57.4 GB of UTF-8 text across their full releases. Scaling those figures by each selected shard's share of the pinned compressed tree gives a **rough 0.96 GB + 1.28 GB = 2.24 GB expanded-text estimate** if both selected shards were fully materialized. That is a planning estimate, not a measured shard ratio. The proposed native path streams gzip, retains at most 64 MiB of selected rows and removes temporary compressed inputs after verification; it should not write the full 2.24 GB as decoded files. Expect peak additional disk below roughly 1.5 GiB, with the 5 GiB hard cap covering staging, receipts and failures. A code change that retains full shards or writes full decoded text must revise this estimate and cap before any transfer.

## Native transport prerequisite

The current bounded Hugging Face adapter already fetches an entire named `.json.gz` shard, streams a row prefix, checks a declared SHA-256 and limits retained rows/bytes. It **cannot execute this exact proposal yet**:

1. `HFBoundedShard` validation in `src/sparselab/corpus/project.py` requires config and split markers in the filename. These exact Common Pile names have neither `default` nor `train`, although the dataset metadata reports `default`/`train`. Add a narrow exact-file preflight using the pinned repository tree and dataset config/split metadata; do not mislabel the split to satisfy filename validation. Reject missing or ambiguous metadata.
2. Add an aggregate, durable **transfer ledger** to the existing bounded-shard acquisition path. Bind it to the attempt ID, two source revisions/files and one deadline; reserve the declared full-file size atomically before each source request, charge failed reservations, and refuse a fourth transfer or any reservation exceeding 1,323,415,169 source-body bytes. Bound metadata responses by their separate 1,048,576-byte allowance. Count actual response-body bytes while streaming and stop before either a per-file reservation or the combined 1,324,463,745-byte allowance is crossed. Persist and verify the ledger across process restarts so a retry or resumed command cannot reset it. Disable unaccounted automatic retries and cache fetches. Record actual and charged bytes, attempts, SHA checks, row/output counts and failures in native receipts.

Use the existing native `corpus` acquisition/release and verification commands after those focused fixes pass tests; do not build a task-specific downloader. The pilot has **no Git input**, so the current Git adapter's post-fetch `max_bytes` is not used as a transport bound. PagerDuty's 36 pinned Markdown files need a separate file-level rights and bounded-transport proposal before any Git/content fetch. Before an approved launch, finish and test the focused code change, run applicable local checks, commit the fixed revision, inspect the effective declaration and output locations, and record source commit/package identity. No check is represented here as already run.

## Rights and scientific stop rules

- Before raw transfer, review the pinned component cards, Project Gutenberg's [license policy](https://www.gutenberg.org/policy/license) and Wikimedia's applicable [reuse/attribution terms](https://foundation.wikimedia.org/wiki/Policy:Terms_of_Use); document that this is a restricted **rights-review acquisition**, not permission to use all rows for training or redistribution. Stop if source-level terms cannot support that limited review.
- For each selected Project Gutenberg record, preserve ID, title, origin URL, provenance, asserted license and content digest; check the particular edition/work's public-domain or permission basis for the intended jurisdiction, embedded notices, Project Gutenberg trademark/header treatment, and any third-party material. Quarantine missing or conflicting rights evidence.
- For each selected Wikimedia record, keep source wiki/page URL, namespace, revision/date, author/history route, asserted license, imported-text notices and content digest. Admit only individually reviewed English content-namespace pages with a traceable attribution route; quarantine empty/mismatched author metadata, third-party material, talk/user pages and uncertain license terms. Preserve CC BY-SA attribution/share-alike obligations for any later allowed use.
- Record every selected, excluded and unavailable sampled row with reason; do not silently fill quotas. Unscanned and unselected rows remain unreviewed and ineligible. Before any later tokenizer fit or training, freeze source-family splits, cross-source exact/near-duplicate checks and answer exclusions under the Card 03 contract. This pilot produces **no** measured mixture, tokenizer coverage or evaluation score.
- Stop on any cap, source/rights mismatch, checksum failure, missing ledger, unexpected redirect/cache behavior, malformed row, or insufficient storage margin. Preserve negative and partial receipts. A completed download alone does not satisfy Card 03 or Gate 0.

This ingestion-pilot allocation is independent of the later language-training **target-token, optimizer-update and GPU-time budgets**. No training tokens or updates can be borrowed from it. The proposed main architecture stays at **341,885,952 parameters** with vocabulary 32,768, width 1,024, 24 layers, 16 heads and FFN 2,816; no config or checkpoint changes are requested. Owner approval of this exact pilot would still be conditional on the native transport prerequisite and source-level rights review passing before acquisition.
