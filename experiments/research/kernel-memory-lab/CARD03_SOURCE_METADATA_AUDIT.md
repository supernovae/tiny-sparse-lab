## Correction to the S1 preparation request

The S1 request for a **64 MiB downloaded-source** pilot covering both Common Pile and PagerDuty cannot be executed as written. Even the smallest listed compressed shard in each proposed Common Pile component exceeds 64 MiB. Native `src/sparselab/corpus/acquisition.py` downloads a complete Hugging Face bounded shard before selecting rows. Its Git path runs `git fetch --depth=1` before applying `max_bytes` to selected blobs, so selecting 302,785 bytes of Markdown does not bound Git network/cache transfer; the repository also contains a 79,292,706-byte PDF. These are preflight blockers, not measured transfer or rights failures. **Do not start S1's pilot or silently raise its cap.** Its 15-minute CPU, 1 GiB disk and zero-update figures remain historical proposals, not approvals.

The smallest next Card 03 task is a **file-level rights and bounded-transport plan**, with no corpus download: inspect the 36 pinned Markdown pages and component metadata/terms, record per-file exclusions and attribution, and specify a native transport that either proves a network/cache cap before fetching or stops without fetching. Its acceptance is a signed-off exact file/rights inventory and a separately reviewable acquisition request with actual input sizes, transport behavior, decoded-output/disk estimate and stop conditions. A PagerDuty-only text pilot may then be proposed separately; no Common Pile shard enters that small pilot. Any full Common Pile shard or tokenizer fit needs a new allocation after item-level rights review. No optimizer or GPU work is implicated.

Card 03's specification and pilot design are **ACCEPTED for reuse** under KML-D06, with full acceptance blocked on rights-cleared source rows, separately approved acquisition, realized split/tokenizer/items and their review.
